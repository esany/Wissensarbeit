## 8. Root-cause synthesis

The long-chat audits support four connected root causes. They remain candidate synthesis until later design work independently confirms them.

### RC-1 — Persistence stronger than active-state lifecycle

Recognized material state is reliably externalized, but the system has a weaker generic mechanism for deciding when persisted information becomes historical, superseded, evidence-only or no longer default context.

Effect: history grows; active cognitive surface does not shrink at the same rate.

### RC-2 — Execution/assurance stronger than programme navigation

Once work is selected, bounded execution, review, evidence and reconciliation are comparatively strong.

After closure, however, the remaining strategic landscape is repeatedly reconstructed from a large evidence surface instead of being durably reduced by programme-level disposition.

### RC-3 — Development semantics are present but not adaptively operationalized

Lifecycle and Building Blocks already carry the correct non-linear semantics. The gap is not a missing linear process; it is the missing operational ability to derive proportionally:

`what must still be understood/researched/required/designed before implementation is admissible?`

### RC-4 — Learning is persisted more reliably than converted into system effect

Learnings appear in audits, Issues, candidate contracts and Failure Evidence, but their downstream disposition into method correction, regression, requirement candidate, design principle, project evidence or no-change is not equally strong.

## 9. Repeating empty-state / reconstruction loop

Observed pattern across later work:

```text
Human/material priority chosen
-> bounded current work
-> good implementation/evidence/review/closure
-> execution successor deliberately not inferred
-> follow_up = not-derived
-> programme landscape reconstructed from #7 + repo/history
-> new candidate comparison
-> Human chooses again
```

The `not-derived` boundary correctly protects Human priority authority. The failure is not that the AI refuses to invent a priority. The failure is that the programme/problem state is not compactly updated so the Human can decide from a reduced, current landscape.

## 10. Development planning != solution planning

A durable learning of this chat is the distinction:

**Development planning** asks:

- what problem/evidence must be synthesized?
- which requirements need disposition?
- what uncertainty remains?
- what research is needed?
- what concepts must later be compared?
- what design decision must eventually be made?

**Solution planning** asks how an already selected design will be implemented.

The second must not be performed before the first has provided sufficient evidence for solution commitment.

The useful Human heuristic remains:

`Problem -> Analysis -> Requirements -> Research -> Concept -> Design -> Implementation -> Test -> Learning -> Iteration`

but it is **not a mandatory linear pipeline**. It is a modular/re-entry-capable set of development capabilities. Small obvious changes may legitimately skip steps; material systemic changes may not call themselves lean by omitting necessary epistemic/design work.

## 11. Wirknetz x Development Method x Skill organism

Current system-level candidate relation:

```text
semantic problem state / Wirknetz perspective
-> material method need
-> capability need
-> bounded Skill or Skill composition
-> result + evidence + uncertainty
-> systemic/semantic reconciliation
-> changed problem state / learning
-> re-entry as needed
```

Boundary rules:

- Wirknetz is not automatically an ontology or storage schema.
- Skill organism is not a project planner or authority system.
- Task Compilation must not silently own Intent interpretation or method internals.
- Capability selection must preserve provenance/uncertainty needed for the downstream method.
- Result integration must state impact, not merely emit an artifact.
- relation correctness outranks graph completeness.

The prior Track-B thin-bridge concept is useful design evidence, not an accepted architecture.
